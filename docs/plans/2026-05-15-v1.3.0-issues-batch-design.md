# v1.3.0 — Issue Batch Fix Design

## Goal

Close the six open GitHub issues (#6 – #11) as one coordinated `v1.3.0` release. The release simultaneously closes a real LAN-content-disclosure security hole, eliminates two silent-data-loss bugs (mid-review hot-reload, swallowed submit errors), repairs two pieces of broken UX (no-op tab close, mobile sidebar pushing content offscreen), and corrects attribution drift left over from the original `md-review` fork.

The release ships through the existing release-please workflow → `npm publish --access public --provenance` pipeline.

## Constraints

- **One release, one changelog story.** Every fix lands as a single conventional commit so release-please auto-bumps `1.2.0 → 1.3.0` based on `feat:` / `fix:` prefixes.
- **TDD for the behavior changes that have failure modes** (#6 bind, #7 ID stability, #11 submit error). UI-only fixes (#8 strings, #10 mobile CSS) don't need new tests beyond visual confirmation.
- **No backwards-compatibility shims for #6.** The default bind change is intentional and small-impact; the `--host` flag is the documented restore path. Changelog calls it out plainly.
- **YAGNI on persistence.** #7 fix is in-memory only. Cross-session preservation isn't reported as a bug; defer until users hit it.
- **Attribution must be legally correct.** MIT requires preserving the upstream copyright. The fix adds Seiraiyu/David's copyright alongside the existing line, not in place of it.
- **No new dependencies.**

## Architecture

The fix touches five distinct surfaces that don't share state. Each phase is independent and can be developed in parallel — order in the plan reflects risk (security first, attribution last).

### Phase 1 — Bind default + `--host` flag


**`bin/md-review-plus.js`**: parse `--host <addr>`, validate, propagate via `process.env.API_HOST`.

```js

default: { ..., host: '127.0.0.1' },

// in arg processing

```

**New file `bin/host-validate.js`** (CommonJS export so both CLI entry and tests can import):

```js
// Accept: 127.0.0.1, localhost, 0.0.0.0, any IPv4 dotted-quad, IPv6 [::1]/[::]/etc.
export function validateHost(host) {
  if (host === "localhost" || host === "127.0.0.1" || host === "0.0.0.0")
    return null;
  if (host === "::1" || host === "::") return null;
  if (/^(\d{1,3}\.){3}\d{1,3}$/.test(host)) {
    const ok = host.split(".").every((o) => parseInt(o, 10) <= 255);
    return ok ? null : `Invalid IPv4 address: ${host}`;
  }
  if (/^[0-9a-fA-F:]+$/.test(host) && host.includes(":")) return null; // permissive IPv6
  return `Invalid --host value: ${host}. Use 127.0.0.1, localhost, 0.0.0.0, or an explicit IP.`;
}
```

**Help text update** in `bin/md-review-plus.js`:

```
--host <addr>          Bind address (default: 127.0.0.1).
                       Use 0.0.0.0 for LAN access; prefer --remote for cross-machine review.
```

### Phase 2 — Stable section IDs

**`src/hooks/useSections.ts`**: replace single-call `generateId(heading, index)` with batch `generateIds(headings)`:

```ts
function slugify(s: string): string {
  return s
    .toLowerCase()
    .replace(/[^a-z0-9]+/g, "-")
    .replace(/^-|-$/g, "");
}

function generateIds(headings: string[]): string[] {
  const counts: Record<string, number> = {};
  return headings.map((h) => {
    const slug = slugify(h) || "section";
    counts[slug] = (counts[slug] ?? 0) + 1;
    return counts[slug] === 1
      ? `section-${slug}`
      : `section-${slug}-${counts[slug]}`;
  });
}
```

`parseMarkdownSections` calls `generateIds(headings)` once, then assigns IDs by index into the result. `sectionState` keying logic is unchanged — the map key is the new stable ID, and `sectionState.get(id)` now hits across heading reorder.

**Behavioral consequences:**

- Heading reorder: state preserved ✓
- Heading addition above an in-progress section: state preserved ✓
- Heading removal above an in-progress section: state preserved ✓
- Heading rename: state lost (slug changes → new ID). Acceptable: rename is a semantic change worth re-reviewing.
- Two headings with the same text: deterministic (`section-foo`, `section-foo-2`).

### Phase 3 — Submit terminal screens

**`src/components/CliModeApp.tsx`**:

```tsx
type SubmitState =
  | { state: "idle" }
  | { state: "submitting" }
  | { state: "submitted" }
  | { state: "error"; message: string };

const [submit, setSubmit] = useState<SubmitState>({ state: "idle" });

const handleSubmit = async (payload: SubmitPayload) => {
  setSubmit({ state: "submitting" });
  try {
    const res = await fetch("/api/submit", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(payload)
    });
    if (!res.ok) throw new Error(`server returned ${res.status}`);
    setSubmit({ state: "submitted" });
  } catch (e) {
    const message = e instanceof Error ? e.message : "unknown error";
    setSubmit({ state: "error", message });
  }
};

if (submit.state === "submitted") return <SubmittedScreen />;
if (submit.state === "error") {
  return (
    <SubmitErrorScreen
      message={submit.message}
      onRetry={() => handleSubmit(/* re-pass the payload */)}
    />
  );
}
// fall through to ReviewView for idle + submitting
```

Submit re-pass: the easiest way to retry is to keep the last-submitted payload in a ref. The ReviewView is unmounted while error screen shows, so we can't re-derive it.

## Error handling

| Surface        | Failure mode                                     | Behavior after fix                                                                                                                   |
| -------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ | --- | ---------------------- |
| Server bind    | Port + host combination busy                     | Same `EADDRINUSE` retry loop (port increment). If `127.0.0.1` is denied (rare), error bubbles up via `server.once('error')`.         |
| `--host` flag  | Invalid value                                    | `validateHost` returns error string; CLI exits 1 before spawning server. Unit-tested.                                                |
| `useSections`  | Empty heading text after slugify (all non-alnum) | Fallback ID `section-section`, `section-section-2`, etc. via the `                                                                   |     | 'section'` in slugify. |
| Submit fetch   | Network error / 5xx / server gone                | Caught, surfaced as `SubmitErrorScreen` with the underlying message. Retry button re-invokes `handleSubmit` with the cached payload. |
| Submit fetch   | `!res.ok` (4xx)                                  | Same path — error message includes status code.                                                                                      |
| Mobile sidebar | Browser doesn't support CSS attribute selectors  | Already universal; fallback would just show the sidebar (the current bug) — acceptable as graceful degradation.                      |
| Attribution    | Bad JSON in package.json after edit              | `bun install` would fail; caught in CI.                                                                                              |

## Release flow

1. All 5 phases land as separate commits on `main` (or one branch merged in one PR — same effect for release-please).
2. Commit prefixes:
   - Phase 1: `fix(server): bind to 127.0.0.1 by default; add --host flag (#6)`
   - Phase 2: `fix(web): stable slug-based section IDs survive hot-reload (#7)`
   - Phase 3: `feat(web): terminal submit screens with retry (#9, #11)`
   - Phase 4: `fix(web): hide empty comments sidebar on narrow viewports (#10)`
   - Phase 5: `chore: rebrand UI strings, fix package.json attribution, add Credits (#8)`
3. release-please updates the open Release PR to propose `v1.3.0` with all four `fix:` + one `feat:` aggregated into the changelog.
4. Merge the Release PR → workflow creates the GitHub release → `publish` job runs `npm publish --access public --provenance`.
5. Smoke-test: `bunx md-review-plus@1.3.0 test-samples/sample.md --review --no-open` and verify the full happy path.

- Refactoring `RemoteModeApp` error path to share `<SubmitErrorScreen>` — optional polish only if free; otherwise leave both screens parallel.
- Re-introducing dark mode — was deliberately removed in v1.2.0.
- Funding link target — left empty until there's a Seiraiyu sponsor URL to point to.
